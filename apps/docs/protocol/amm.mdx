## What kind of AMM this is

A Notional Finance-style logit/"rate anchor" curve operating on **PT face value vs. underlying-asset value** — not raw SY shares, and not a plain constant-product `x*y=k` curve. All curve math happens in asset-denominated units; SY-share conversion happens only at the swap boundary.

## Units

| Variable | Unit |
|---|---|
| `state.total_pt` | PT face units |
| `state.total_sy` | SY share units |
| `total_asset` (working value, not stored) | underlying-asset units, `= floor(total_sy * rate / WAD)` |
| `state.last_ln_implied_rate`, `twap_ln_implied_rate` | WAD-scaled, natural log of the annualized implied rate |
| `config.fee_bps` | basis points, `0–9999`, denominator `10_000` |
| `config.scalar_root`, `initial_anchor` | WAD-scaled curve-shape parameters |

## Constants

- `WAD = 10^18`
- `BPS_DENOMINATOR = 10_000`
- `IMPLIED_RATE_TIME = 365 days` (annualization basis)
- `MINIMUM_LIQUIDITY = 1000` — burned on the first LP mint (Uniswap-style, prevents a degenerate near-zero-supply LP token)
- `MAX_MARKET_PROPORTION = 96% of WAD` — a swap that would push PT's share of the pool above this reverts with `MarketProportionTooHigh`
- `MAX_RESERVE_UNITS = WAD`, `MAX_SCALAR_ROOT = 10·WAD`, `MAX_ANCHOR = 2·WAD` — conservative input-bound caps; the source comment notes re-deriving the exact i128 overflow bound is still open work

## Rate scalar and rate anchor

The curve's steepness scales inversely with time to maturity:

```
rate_scalar = scalar_root * IMPLIED_RATE_TIME / time_to_expiry
```

The anchor recalibrates on every call so implied rate stays continuous as time passes with no trades in between:

```
exchange_rate_from_rate = exp(last_ln_implied_rate * time_to_expiry / IMPLIED_RATE_TIME)
```
(must be `>= WAD`, else panics `ExchangeRateBelowOne` — see [Known Findings](/security/known-findings) for the investigation into this)

```
proportion      = total_pt * WAD / (total_pt + total_asset)
ln_proportion   = ln(proportion / (1 - proportion))          // logit
rate_anchor     = exchange_rate_from_rate - ln_proportion * WAD / rate_scalar
```

## Exchange rate at a given trade size

```
proportion    = (total_pt - net_pt_to_account) * WAD / (total_pt + total_asset)
                // reverts MarketProportionTooHigh if > MAX_MARKET_PROPORTION
ln_proportion = ln(proportion / (1 - proportion))
exchange_rate = ln_proportion * WAD / rate_scalar + rate_anchor
                // floored at WAD; reverts ExchangeRateBelowOne otherwise
```

## Implied rate

```
ln_implied_rate = ln(exchange_rate) * IMPLIED_RATE_TIME / time_to_expiry
implied_rate_bps = ln_implied_rate * 10_000 / WAD
```

This is a **continuously-compounded annualized rate**, not a simple APY — treat `spot_apy()`/`twap_apy()` accordingly when displaying them.

## PT → SY (exact-in)

```
exchange_rate       = get_exchange_rate(net_pt_to_account = -pt_in)
pre_fee_asset_out   = pt_in * WAD / exchange_rate
fee                 = pre_fee_asset_out * fee_bps / 10_000
asset_out           = pre_fee_asset_out - fee
sy_out              = floor(asset_out to SY units)
```

Reverts `InsufficientLiquidity` if `sy_out <= 0` or `sy_out >= total_sy` — the pool can never be fully drained by a single swap.

## SY → PT (exact-in)

PT-out is solved via **binary search** for the largest `pt_out` whose required SY cost — computed the same way as an exact-PT-out quote, with the fee added on the input side (`asset_in = pre_fee_asset_in + fee`, ceil-rounded) — fits within the SY provided.

## SY → YT (exact-in)

`solve_yt_out_for_sy_in` also binary-searches, this time for the largest `yt_out` whose PT-leg cost (via `try_exact_pt_in_sy_out`) leaves the buyer at or under the SY they provided — a candidate is only accepted if it fits within `sy_in`, so the result can be suboptimal for the buyer but is never unsafe for the pool.

## Fee model

A single `fee_bps` rate is charged on the **asset-denominated leg** of every PT⟷SY trade: subtracted from the output on exact-PT-in trades, added to the input on exact-PT-out trades. There is no separate protocol fee split documented in the current contract — all fee revenue accrues to the pool (and therefore to LPs) directly.

## SY ⇄ YT: no separate curve

`swap_sy_for_yt`/`swap_yt_for_sy` don't have their own pricing curve. They're synthesized by flash-splitting or flash-recombining PT/YT through the tokenizer within the same transaction, converting the curve's PT-face amounts to/from tokenizer SY-share amounts via ceil/floor-mirrored helpers that match the tokenizer's own rounding. This means YT price is **entirely derived** from the PT/SY curve plus the live SY rate — see [Data Flow](/architecture/data-flow) for the call sequence.

## Reserve accounting: reconciliation, not pure tracking

`state.total_pt`/`total_sy` are updated analytically mid-computation on every swap/liquidity call, but every mutating entrypoint ends by calling `reconcile_reserves()`, which re-reads the pool's actual on-chain PT/SY token balances and overwrites the stored state with those real values. **The persisted reserves are always exactly what the pool holds** — the analytic values are a working intermediate, never the source of truth, which guards against rounding-dust drift accumulating over many trades.

## TWAP

`sync_twap()` does an elapsed-time-weighted blend of `ln_implied_rate` into the TWAP (`weight = elapsed / twap_window`) — a single-step exponential-moving-average style blend, not a true cumulative-sum TWAP. If the gap since the last observation is `>= twap_window`, it **snaps to the latest observation and re-enters a warm-up period** (`warmup_until = now + twap_window`) rather than trusting a stale average — an explicit anti-manipulation measure against a long-idle-then-single-large-trade attack.

## Rounding conventions

| Direction | Rounding |
|---|---|
| SY paid out to a trader | floor |
| SY charged to a trader | ceil |
| LP mint amounts (first mint) | `isqrt(pt_in * sy_in)`, floor, minus `MINIMUM_LIQUIDITY` |
| LP mint amounts (subsequent) | proportional, min of the two ratios; used token amounts rounded up to match the minted LP share |
| `remove_liquidity` payouts | floored, pro-rata by LP share |

## Transcendental math

Soroban wasm forbids floating point, so `ln_wad`/`exp_wad` are custom fixed-point implementations using integer range-reduction plus a Taylor/atanh series.
